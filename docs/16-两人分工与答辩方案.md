## 二、假设说明

1. **项目真实情况已知**：后端 `server/src/`（入口 `app.js`，路由 `routes/`、控制层 `controllers/`、数据层 `db/`、中间件 `middleware/`、工具 `utils/`）；前端 `web/`（顾客端页面 + `admin/` 管理端 + `assets/js/` 脚本）；数据库 `server/data/flower.db`，10 张表；接口清单在 `docs/03-接口文档.md`。
2. **技术栈固定**：Express + Node 内置 `node:sqlite` + 原生 JS/CSS，不用 React/Vue，不引入第三方 ORM 和图表库。答辩演示前后端分开跑：后端 IDEA 3000，前端 Node 5173。
3. **分工原则**：按「端到端模块」切，不按「层次」切。即 A 负责若干完整业务（从接口到页面数据），B 负责若干完整页面（从界面到调用），避免一人只写路由、另一人只写样式导致谁都讲不全。
4. **角色可整体对调**：若 B 更强于后端，把 A/B 的模块整块交换即可，其余（协作接口、进度、答辩结构）不变。
5. **组长职责不等于多干活**：A 的重点是「定契约、控进度、把关合并、补缺口」，具体代码量尽量与 B 均衡。
6. **时间用相对周次**：请把「第 N 周」替换成你的真实日期；若只剩 2 周，按 5.4 的压缩版执行。

### 3.3 任务边界（防扯皮四条）

1. **文件归属唯一**：A 只改 `server/**` 与 `docs/03`；B 只改 `web/**` 与 `docs/04`。`schema.sql` 归 A；`api.js` 归 B。跨边界改动必须先说一声。
2. **接口变更走文档**：任何人要改接口路径/参数/返回结构，**先在 `docs/03-接口文档.md` 改并通知对方**，对方确认后再改代码。禁止私下改完不通知。
3. **数据库结构归 A**：B 需要新字段先提给 A，由 A 统一加表/字段并同步 `schema.sql`，避免两边各建各的库。
4. **冲突处理**：以 main 分支为准；谁的功能先合谁优先，后合者负责自己解决冲突；每天收工前互相同步一次进度。

### 5.2 A（组长）讲解要点

**个人贡献**：项目骨架与数据库设计；认证鉴权、商品/购物车/订单/支付全部后端接口；下单事务与订单状态机；接口文档与联调统筹。

**实现思路**：前后端分离，后端按「路由→控制层→数据层」分层；路由只做分发与权限门禁，控制层写业务，数据层统一 SQL 与事务；RESTful 接口 + 统一返回 `{code,message,data}`；用 Node 内置 SQLite 实现零外部数据库依赖。

**成果展示要点**：
- 现场演示「注册→登录→浏览→加购→下单→支付→后台发货→确认收货」完整闭环
- 展示 `schema.sql` 十张表与外键关系，指出订单明细的**价格/名称快照**避免历史订单受改价影响
- 展示下单事务：库存不足时整单回滚，库存正确扣减

**难点与解决方案**：
1. **库存超卖 / 下单一致性** → 用事务包裹「查库存→生成订单与明细→扣库存→清购物车」，任一步失败全部回滚（对应 `order.controller.js` 的下单逻辑）。
2. **JWT 无状态登出** → 用 jti 黑名单：登出时把该 token 的 jti 记入内存集合，校验时命中即失效（`middleware/auth.js`）。
3. **SQL 注入防护** → 参数化查询 + 排序字段白名单（`flower.controller.js` 的 `SORT_MAP`）。
4. **无第三方依赖** → 自研 JWT、scrypt 密码、参数校验、SVG 图表，全部用 Node 内置能力，降低部署与答辩环境风险。

**可能被问及回答思路**：
- 「为什么不用 MySQL？」→ 毕业设计规模小，SQLite 单文件零部署、易拷贝演示，功能完全够用；代码里通过 `db/` 层封装，将来换库改动集中在数据层。
- 「如何保证订单状态不乱？」→ 订单表 `status` 字段定义 pending→paid→shipped→completed，加 canceled；每次流转在控制层校验当前状态，非法跳转拒绝。
- 「重启后 token 为什么失效？」→ JWT 密钥未配置时每次启动随机生成，属于预期的无状态会话行为；正式部署可在 `.env` 配固定密钥。

### 5.3 B（组员）讲解要点

**个人贡献**：前端公共层与独立服务；顾客端 11 个页面、管理端 6 个页面的界面与交互；移动端适配与 SVG 图表；测试用例与演示素材。

**实现思路**：一页一个 HTML 配同名 JS，公共能力抽到 `api.js`/`ui.js` 复用；`api.js` 统一封装 fetch、token、401 跳转、超时与错误提示；前后端分离通过 `web/server.js` 把 `/api` 转发到后端，前端代码无需关心地址。

**成果展示要点**：
- 展示列表页的搜索、分类/价格筛选、排序、分页联动
- 展示购物车与结算流程、订单详情时间轴
- 展示管理端看板图表与商品/订单/评价管理
- 切换窗口演示移动端适配效果

**难点与解决方案**：
1. **前后端分离下的请求统一** → `api.js` 做一层封装，所有页面只调 `API.get/post`，自动带 token、解包 `data`、统一错误提示。
2. **登录过期处理** → 后端返回 401，前端去重跳转登录页并带上 redirect 参数，避免多个并发请求反复跳。
3. **页面多且易乱** → 按功能/页面分类命名，顾客端在 `web/` 根、后台在 `admin/`，样式按 base/layout/shop/mobile/admin 分文件。
4. **图表零依赖** → 用自研 SVG 绘制看板图表，避免引入大型图表库。

**可能被问及回答思路**：
- 「为什么不用 Vue/React？」→ 项目规模与教学要求下，原生 JS 足够，减少构建工具与依赖，答辩环境更稳、代码更透明可控。
- 「跨域怎么解决？」→ 同源部署时后端直接托管前端；分开启动时前端服务把 `/api` 代理到后端，浏览器看仍是同源，无需 CORS 特殊处理。
- 「页面这么多怎么维护？」→ 一页一 HTML 一同名 JS，公共逻辑抽离、命名与页面一致，改一个不影响其他。

### 5.4 两人共同准备

- **交叉问答**：A 必须能说清前端怎么调接口，B 必须能说清后端接口返回什么；互考 5.2/5.3 的「可能被问」清单。
- **统一口径**：项目背景、架构图、数据库表数（10 张）、技术栈说辞两人一致，不能一人说 MySQL 一人说 SQLite。
- **演示预案**：后端未启动 / 端口占用 / token 过期三种情况分别怎么应对，提前演练；演示前先 `npm run reset`。
- **诚实边界**：不夸大有 service 层、不声称用了框架或缓存；被问到"哪里可以改进"可答：加真实支付网关、引入缓存与消息队列、加自动化测试覆盖率——这体现思考深度。
