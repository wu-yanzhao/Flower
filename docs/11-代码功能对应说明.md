## 0. 架构与请求链路（先背这一段）

| 层次 | 主要文件 | 职责 |
| --- | --- | --- |
| 前端静态服务 | `web/server.js` | 零依赖 Node 静态服务器；托管 `web/`，把 `/api/*` 转发给后端 |
| 前端页面 | `web/*.html`、`web/admin/*.html` | 顾客端 11 个页面、管理端 6 个页面 |
| 前端公共层 | `web/assets/js/{api,ui,layout,components,chart}.js`、`web/assets/js/admin-layout.js` | 请求封装、UI 组件、布局守卫、自研 SVG 图表 |
| 路由层 | `server/src/routes/*.js` | URL → 控制器映射，挂载鉴权中间件 |
| 控制器层 | `server/src/controllers/*.js` | 业务编排：校验 → 查库 → 事务 → 响应 |
| 中间件/工具层 | `server/src/middleware/*`、`server/src/utils/*` | 鉴权、限流、日志、统一响应、JWT、scrypt、参数校验 |
| 数据层 | `server/src/db/{index,driver}.js`、`schema.sql` | `node:sqlite` 连接、事务包装、10 张表、首次运行灌种子数据 |

**一次请求的完整链路（答辩标准答案）：**
浏览器页面 JS → `api.js` 的 `request()` 自动加 `Authorization: Bearer <token>` → `web/server.js` 把 `/api/*` 转发到 `localhost:3000` → `app.js` 的中间件（安全头、CORS、JSON 解析、日志） → `routes/*.js` → 鉴权中间件 → `controllers/*.js` → `db/driver.js` 包装的 SQLite → 统一 `{ code, message, data }` 响应回到前端 `UI.toast` / 页面渲染。

**核心文件定位口诀：**
_入口看 `app.js`，接口看 `routes`，业务逻辑看 `controllers`，数据库看 `db`，页面交互看 `web/assets/js` 与 `web/admin/js`。_

## 1. 基础设施与工程规范

### 1.1 后端服务启动与全局中间件
- **对应文件/函数**：`server/src/app.js` → `createApp()`（第 14 行）、`start()`（第 80 行）；`config.js` → `loadEnvFile()`（第 10 行）
- **关键实现位置**：app.js:15 初始化数据库；:22 安全头；:27-39 CORS；:43-44 图片接口单独放宽到 16mb、其余 1mb；:50/:59 静态资源托管；:66 登录限流；:69 挂载 `/api`；:74-75 404 与错误处理；:82-86 Node ≥22.5 版本校验；:104 端口占用友好提示
- **核心逻辑**：先建库再建 Express 应用；用中间件流水线统一处理安全、跨域、解析、日志、静态资源；配置全部集中在 `config.js`，`.env` 可选覆盖，JWT 密钥未配置时随机生成（避免内置弱密钥）
- **输入/输出**：输入 = 环境变量（`PORT`、`JWT_SECRET`、`CORS_ORIGINS`、`DB_FILE` 等）；输出 = 监听 3000 端口的 HTTP 服务 + 控制台启动横幅
- **依赖/调用**：`config.js` → `db/index.js` → `routes/index.js` → `middleware/error.js`、`middleware/security.js`
- **答辩概括**："后端入口只有 120 行，做三件事——初始化数据库、注册中间件、挂载路由。安全头、限流、日志都做成可复用中间件，业务控制器只关心业务，这就是分层的好处。"

### 1.2 数据库初始化、驱动适配与事务
- **对应文件/函数**：`db/index.js` → `initDatabase()`（第 11 行）、`migrate()`（第 32 行）、`logOperation()`（第 44 行）；`db/driver.js` → `createConnection()`（第 21 行）、`makeTransaction()`（第 45 行）、`wrap()`（第 86 行）；`schema.sql`
- **关键实现位置**：driver.js:15 使用 Node 内置 `node:sqlite`（零安装免编译）；:27 开启外键；:45-77 事务支持嵌套（顶层 BEGIN/COMMIT/ROLLBACK，嵌套用 SAVEPOINT）；index.js:23-26 空库自动灌演示数据；schema.sql:7-163 共 10 张表
- **核心逻辑**：把驱动差异封装成 `all/get/run/exec/transaction` 五个方法，业务层只面对统一接口；表全部 `IF NOT EXISTS`，启动不破坏数据；轻量迁移给旧库补 `discount_amount`、`rating` 列
- **输入/输出**：输入 = `data/flower.db` 路径 + `schema.sql`；输出 = 可用的 db 对象和 driver 名称
- **依赖/调用**：被 `app.js:15` 调用；所有控制器通过 `req.app.locals.db` 使用；`order/cart/address/review` 控制器用 `db.transaction()`
- **答辩概括**："我用 Node 22 内置的 `node:sqlite`，把连接和事务封装成适配层，业务代码只写 `db.run/get/all`。事务支持嵌套 SAVEPOINT，所以下单、取消回滚这些多步操作能保证要么全成功要么全回滚。"

### 1.3 统一响应、校验、错误与安全工具
- **对应文件/函数**：`utils/response.js` → `ok()`（第 13 行）、`page()`（第 18 行）、`asyncHandler()`（第 33 行）；`utils/validate.js` → `validate()`（第 25 行）；`middleware/error.js` → `requestLogger()`（第 9 行）、`errorHandler()`（第 36 行）；`utils/http-error.js`
- **关键实现位置**：response.js:14 统一 `{code:0,message,data}`；:18 分页固定返回 `list/total/page/pageSize/totalPages`；validate.js:30-100 规则表驱动（required/type/min/max/pattern/enum/default），失败抛 `HttpError(400)` 并带字段明细；error.js:39-53 把业务异常和框架异常统一转成 JSON，5xx 才打印堆栈
- **输入/输出**：输入 = `req.body` + 规则对象；输出 = 规范化后的数据对象或带字段级错误信息的 400 响应
- **依赖/调用**：几乎每个控制器都调用 `validate` 和 `ok/page`；路由层用 `asyncHandler` 包裹控制器，异常统一交给 `errorHandler`
- **答辩概括**："我写了一个零依赖的校验器，用规则表描述每个字段，校验失败一次性收集所有错误。所有接口返回同一套结构，前端 `api.js` 只需判断 `code` 是否为 0，错误处理因此非常一致。"

### 1.4 鉴权、JWT 与口令安全
- **对应文件/函数**：`middleware/auth.js` → `resolveUser()`（第 35 行）、`authRequired()`（第 55 行）、`authOptional()`（第 65 行）、`adminOnly()`（第 75 行）、`revokeToken()`（第 16 行）；`utils/jwt.js` → `sign()`（第 21 行）、`verify()`（第 44 行）；`utils/password.js` → `hashPassword()`（第 11 行）、`verifyPassword()`（第 20 行）
- **关键实现位置**：jwt.js:21-39 自研 HS256（header.payload 用 HMAC-SHA256 签名，payload 带 `jti/iat/exp`）；:49-56 校验 `alg=HS256` 防降级；:66-71 `timingSafeEqual` 防计时侧信道；:73 过期校验；password.js:11-18 scrypt 加盐（N=16384,r=8,p=1），存储格式 `scrypt$N$r$p$salt$hash`；auth.js:13 登出用 jti 黑名单实现服务端失效；:46-48 每次请求回查数据库取最新角色与状态
- **输入/输出**：输入 = `Authorization: Bearer <token>` 或 `?token=`；输出 = `req.user`（含数据库最新角色/状态）或 401/403
- **依赖/调用**：被所有需要登录的路由挂载；`catalog.routes.js:25` 用 `authOptional` 让商品详情对游客开放但登录后可显示收藏状态；`admin.routes.js:16` 统一挂 `adminOnly`
- **答辩概括**："鉴权用自研 HS256 JWT，口令用 Node 内置 scrypt 加盐哈希，数据库里没有明文。每次请求都会回查用户表，所以管理员被禁用或改角色后令牌立即失效；登出通过 jti 黑名单让 token 在服务端真正失效。"

## 2. 顾客端核心功能（按购物流程顺序）

### 2.1 注册 / 登录 / 角色分流
- **对应文件/函数**：后端 `controllers/auth.controller.js` → `register()`（第 15 行）、`login()`（第 44 行）、`profile()`（第 62 行）、`changePassword()`（第 92 行）、`logout()`（第 110 行）；前端 `web/assets/js/auth.js` → `initLogin()`（第 41 行）、`initRegister()`（第 97 行）、`resolveTarget()`（第 30 行）；`api.js` → `Auth`（第 16 行）
- **关键实现位置**：auth.controller.js:28 查重；:31 scrypt 哈希后入库；:39 注册即签发 token；:52-55 登录统一错误文案 + 状态检查；auth.js:30-38 角色分流（管理员进后台，顾客回来源页）并校验 redirect 防开放重定向；api.js:77-89 只有"本次带 token 的 401"才清凭证跳登录页
- **输入/输出**：`POST /api/auth/register {username,password,nickname,phone?,email?}` → `{token,user}`；`POST /api/auth/login {username,password}` → `{token,user}`；`GET /api/auth/profile` → 用户信息 + `cartCount/favCount/orderCount`

- **答辩概括**："注册时做格式校验和账号查重，密码用 scrypt 加盐后入库，注册成功直接发 token 免二次登录。登录失败统一提示'账号或密码错误'，避免泄露账号是否存在；登录后按角色分流到前台或后台，并校验 redirect 防止开放重定向。"

### 2.4 购物车与满减金额汇总
- **对应文件/函数**：后端 `cart.controller.js` → `add()`（第 23 行）、`update()`（第 50 行）、`check/checkAll`（第 74/85 行）、`list()`（第 9 行）、`buildSummary()`（第 113 行）；前端 `cart.js` → `render()`（第 9 行）、`updateQty()`（第 80 行）
- **关键实现位置**：cart.controller.js:30-37 三重校验（商品存在、已上架、库存足够，且累加后不超过库存）；:35-45 同商品累加而非新建；:113-128 只统计"勾选且在售"的商品，计算小计/件数/满减（≥500 减 50，≥300 减 20）；schema.sql:79 `UNIQUE(user_id,flower_id)` 兜底

### 2.5 收货地址与结算页

### 2.6 下单事务与库存扣减（★核心亮点）
- **对应文件/函数**：`server/src/controllers/order.controller.js` → `create()`（第 35 行）；`utils/helpers.js` → `generateOrderNo()`（第 10 行）
- **关键实现位置**：order.controller.js:48-76 组装商品（立即购买 / 指定 cartIds / 默认勾选商品三种模式）；:86-101 校验收货信息；:104-111 复用 `buildSummary` 算金额；:113 生成 `FS+时间戳+4位随机` 订单号（带唯一性重试）；:116-142 **一个事务内**写订单、写明细、扣库存、加销量、清购物车；:130-135 把商品名/图/价写进 `order_items` 做快照
- **输入/输出**：`POST /api/orders {addressId?,receiver?,phone?,address?,remark?,cartIds?,buyNow?}` → `{orderId,orderNo,payAmount}`
- **依赖/调用**：`db.transaction()`（driver.js:45）→ `buildSummary`（cart.controller.js:113）→ `generateOrderNo`（helpers.js:10）；`schema.sql:113` 的订单明细表实现价格快照
- **答辩概括**："下单是系统最关键的事务。我先补齐并校验商品与收货信息，再在一个数据库事务里完成写订单、写明细、扣库存、加销量、清购物车——任何一步失败就整体回滚，所以不会超卖。明细表存的是下单时的商品快照，后续商品改价也不会影响历史订单。"

### 2.7 模拟支付、取消回滚与订单状态机（★核心亮点）
- **对应文件/函数**：`order.controller.js` → `STATUS_TEXT`（第 11 行）、`TRANSITIONS`（第 20 行）、`pay()`（第 195 行）、`cancel()`（第 208 行）、`receive()`（第 227 行）、`assertTransition()`（第 352 行）；前端 `pay.js` → `startCountdown()`（第 11 行）、确认支付（第 58 行）
- **关键实现位置**：order.controller.js:20-26 状态流转白名单：`pending→paid/canceled`、`paid→shipped/canceled`、`shipped→completed/canceled`；:198 支付前先 `assertTransition`；:213-222 取消订单在事务里回滚库存与销量，并把销量钳制为非负；:344-350 `findOrder` 用 id 或订单号查询并做归属校验（管理员除外）；支付页 30 分钟倒计时纯前端提示
- **输入/输出**：`POST /api/orders/:id/pay {payMethod}` → `{status:'paid'}`；`POST /api/orders/:id/cancel` → 回滚后的 `{status:'canceled'}`；`POST /api/orders/:id/receive` → `{status:'completed'}`
- **依赖/调用**：所有状态变更都先经过 `assertTransition`；取消操作复用 `db.transaction()`；`logOperation` 记录支付/取消日志
- **答辩概括**："我用状态机约束订单流转，白名单之外的操作一律 400，比如已完成的订单不能再支付。取消订单会在事务里把库存和销量一起回滚，并把销量钳到 0 以上，保证数据不会出现负数。支付是模拟的，但字段和时间戳都按真实流程留好了，接第三方支付只需替换 pay 接口内部。"

## 6. 答辩讲解建议（怎么把上面内容讲得高分）

1. **先讲流程，再讲代码**：按"浏览 → 筛选 → 详情 → 加购 → 结算 → 下单 → 支付 → 发货 → 收货 → 评价"演示一遍，每到一环补一句"这里对应 `xxx.js` 的 `xxx()`"。
2. **重点深挖三个亮点**（评委最容易被打动）：
   - 下单事务与库存回滚：`order.controller.js:116-142` + `:213-222`
   - 订单状态机：`order.controller.js:20-26` + `assertTransition`
   - 零外部依赖（内置 SQLite、自研 JWT/scrypt/校验器/SVG 图表）：断网可演示
3. **被问细节时不要慌**：先说"这个功能在 `controllers/xxx.js` 的 `xxx()`"，再说输入是什么、做了哪几步、返回什么，最后补一句为什么这么设计。本文第 2、3 节的六要素就是标准答法。
4. **现场 Debug 加分**：在 IDEA 里给 `order.controller.js:116` 的事务打断点，演示下单时逐步看 `stock` 变化，比口头解释更有说服力。
5. **承认边界要坦诚**：支付是模拟、SQLite 适合单机并发不高，但要能接上"如何扩展"（见 `05-答辩指南.md` 5.3 的 Q5/Q6）。
